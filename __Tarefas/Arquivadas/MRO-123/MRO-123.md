# MRO-123 — Dashboard de Métricas de Encerramento e Gargalos

## Criar painel visual (Dashboard) com métricas de encerramento e gargalos de produção filtrados por Projeto.

A gestão precisa de uma visão macro do status de um projeto selecionado. O dashboard deve focar na velocidade de entrega e nos bloqueios que estão atrasando o cronograma.

Critérios de Aceite:

Filtro Global: O painel deve obedecer a um filtro inicial de "Projeto Selecionado".

Métrica de Encerramento: Gráficos/Cards mostrando a quantidade de tarefas encerradas com quebra por DATA e por EQUIPE.

Métrica de Gargalos: Gráficos/Cards detalhando as quantidades de tarefas paradas/impedidas, agrupadas pelo tipo de pendência (ex: Retida por Material, Falta de Ferramenta, Aguardando Cliente, etc.).

## Solução Técnica
A solução será uma aplicação do tipo control que passará os parâmetros de filtro para uma aplicação do tipo blank que renderizará os gráficos e cards. A aplicação blank será responsável por consultar as tabelas `mro_tasks`, `mro_task_assignments` e `mro_task_resources` para gerar as métricas. Se for necessário exibir grid de dados, podemos usar com iframe aplicações do tipo grid criada com selects especiais para essa tarefa.

> **Item extra (IMPLEMENTADO):** ao iniciar o primeiro assignment, atualizar `actual_start` da task se vazio; ao finalizar o último assignment, atualizar `actual_end` se vazio. Detalhes na seção "IMPLEMENTACAO: Atualizacao automatica de actual_start / actual_end" ao final.

## blank_dash_encerramento

### Dashboard de metricas de encerramento e gargalos

**`reports/blank_dash_encerramento/events/onExecute`**
- Recebe globais `[glo_project_id]`, `[glo_periodo_inicial]`, `[glo_periodo_final]`; fallback projeto 0 + 30 dias; conversao defensiva de datas; debug via `sc_log_add`.
- Cabecalho: badge do projeto, nome completo, status, periodo analisado vs periodo do projeto, botao "Voltar Filtro".
- Cards KPI: Total, Em Execucao, **Encerradas (Periodo)** e Bloqueadas — encerradas respeitam o periodo; demais no estado atual. Cada card linka para a grid filtrada.
- Grafico por Data (colunas): hierarquia de fontes **Manual (verde) -> Producao (azul) -> P6 (cinza)**, com tooltip da fonte.
- Grafico por Equipe (barras): Total x Concluidas **no periodo**, com % no tooltip.
- Grafico Gargalos Bloqueios (rosca): flags com prioridade (Material, Ferramenta, Mao de Obra, Predecessora, Predecessora Manual); clique abre a grid filtrada.
- Grafico Gargalos Pendencias (rosca): `pending_id` por descricao; clique abre a grid com `PEND_<id>`.

### Fonte de dados e hierarquia (encerramento)

1. `mro_tasks.actual_end` (manual/DIGEX) — mais confiavel;
2. `MAX(mro_timesheet.end_time)` por assignment encerrado (producao real);
3. `mro_tasks.updated_at` (fallback P6).

## IMPLEMENTACAO: Atualizacao automatica de actual_start / actual_end nas tasks

> **Implementado e validado** — 10/08/2026. O `actual_start`/`actual_end` de `mro_tasks` agora sao preenchidos automaticamente pelo fluxo de producao, alem do preenchimento manual (DIGEX).

**Regra implementada:**
- Ao **iniciar o primeiro assignment** de uma task (primeiro START), preenche `actual_start` da task **se estiver vazio**.
- Ao **concluir o ultimo assignment** da task (SUPSIG, sem outro assignment ativo), preenche `actual_end` **se estiver vazio**.
- **Nunca sobrescreve** datas ja preenchidas manualmente (DIGEX) — so grava quando o campo esta NULL.

### Onde foi implementado

**1. `tasks/form_public_mro_task_assignments/button/Play` (INICIO):**
- Apos criar o timesheet e gravar o evento, se `$tipo_evento == 'START'` (primeiro inicio, nao RESUME):
```php
if ($tipo_evento == 'START') {
    sc_exec_sql("UPDATE mro_tasks
                 SET actual_start = COALESCE(actual_start, NOW())
                 WHERE task_id = (SELECT task_id FROM mro_task_assignments WHERE assignment_id = " . (int){assignment_id} . ")
                   AND actual_start IS NULL");
}
```

**2. `Timesheet/control_pause_task/events/onValidateSuccess` (FIM):**
- Apos fechar o timesheet e atualizar `actual_qty_hours`, se `$status_code == 'SUPSIG'` (conclusao) e nao restar outro assignment ativo:
```php
if ($status_code == 'SUPSIG') {
    sc_exec_sql("UPDATE mro_tasks
                 SET actual_end = COALESCE(actual_end, NOW())
                 WHERE task_id = (SELECT task_id FROM mro_task_assignments WHERE assignment_id = $v_ass_id)
                   AND actual_end IS NULL
                   AND NOT EXISTS (
                       SELECT 1 FROM mro_task_assignments
                       WHERE task_id = (SELECT task_id FROM mro_task_assignments WHERE assignment_id = $v_ass_id)
                         AND status_code IN ('IN_PROGRESS','PAUSED','BLOCKED','PENDING_HANDOVER','SUPSIG')
                         AND assignment_id <> $v_ass_id
                   )");
}
```

### Correcao aplicada durante a auditoria

- **Bug encontrado:** a primeira versao do `actual_end` contava o **proprio assignment** no `NOT EXISTS` (que ainda esta `IN_PROGRESS` no momento do UPDATE, pois vira `SUPSIG` depois) → `actual_end` nunca era gravado.
- **Correcao:** condicionar ao `$status_code == 'SUPSIG'` (so conclusao real) e excluir o proprio assignment (`AND assignment_id <> $v_ass_id`).
- **Validacao via MCP:** cenarios reais confirmados — task com 1 assignment ativo grava `actual_end`; task com 2 ativos so grava no ultimo.

### Regra de negocio final

| Rota | `$status_code` | Grava `actual_end`? | Motivo |
|---|---|---|---|
| 4 (Conclusao) | `SUPSIG` + sem outros ativos | SIM | Tarefa 100% concluida |
| 4 (Conclusao) | `SUPSIG` + ha outros ativos | NAO | Outro mecanico continua |
| 3 (Handover) | `PENDING_HANDOVER` | NAO | Vai para programacao |
| 1/2 (Pausa/Bloqueio) | `PAUSED`/`BLOCKED` | NAO | Task em andamento |

### Teste realizado (evidencia)

- **Assignment 15720 / Task 18153 (370026):** concluido via SUPSIG em 10/08/2026 21:16 — `actual_end` gravado automaticamente com a data/hora da conclusao. Confirmado no banco: `actual_end = 2026-08-10 21:16:26`, assignment `SUPSIG`, timesheet `COMPLETED`, evento `SUPSIG` registrado.
- **Impacto no dashboard:** a task concluida passa a ser exibida no grafico "Encerramento por Data" com fonte **Manual (verde)** — pois a hierarquia prioriza `actual_end` preenchido.

### Texto de ajuda para os campos (DIGEX/usuarios)

- **`actual_start`:** "Data e hora em que a tarefa realmente comecou a ser executada no hangar. Preenchido automaticamente no primeiro inicio da atribuicao (START) ou manualmente pela DIGEX. Nunca sobrescreve uma data ja informada."
- **`actual_end`:** "Data e hora em que a tarefa foi efetivamente concluida. Preenchido automaticamente quando o ultimo mecanico conclui a atribuicao (SUPSIG) ou manualmente pela DIGEX. Enquanto houver atribuicao em andamento, permanece em branco."
