## Bugs encontrados e resolvidos

### Bug 1: NRC aprovada pelo cliente ia direto para RELEASED sem criar assignments

**Sintoma (task 28823 `NWB-ROTINA-C002`):** a NRC passou pelo fluxo O&A, foi aprovada pelo cliente (`btn_aprovar_cliente`) e chegou a RELEASED, mas **nenhum assignment** foi criado para as skills alocadas (MO, A4, S4, DIGEX) — o supervisor (william) nao via a task para designar.

**Diagnostico (confirmado via `mro_nrc_approval_log`):**
- Historico da 28823: `SENT_TO_ENGINEERING` -> `SENT_TO_PROG` -> `PROGRAMMING_OK` -> `OA_REVISION` (mro_engine) -> `APPROVED_BY_CLIENT` (18:23:35)
- A criacao de assignments so acontece no `btn_liberar_para_execucao` (que processa `PLANNING/NOT_STARTED/PLANNED`)
- O `btn_aprovar_cliente` apenas setava `RELEASED` sem criar assignments -> task liberada orfa de mao de obra

**Causa raiz:** o status `APPROVED` ("Aprovado (Cliente)") ja existia no `mro_sys_status` e ja era mapeado no `mExibirCardStatus` como "Liberado para execucao", mas o `btn_aprovar_cliente` pulava direto para `RELEASED`.

**Correcao aplicada (2 botões):**
1. **`tasks/form_public_mro_tasks/button/btn_aprovar_cliente`** — status agora vai para `APPROVED` (nao mais RELEASED). Aprovacao do cliente apenas fecha o faturamento O&A; a liberacao efetiva fica para o botao da grid.
2. **`tasks/grid_public_mro_tasks/button/btn_liberar_para_execucao/onRecord`** — adicionado `APPROVED` na condicao de status processavel. Agora, ao liberar, cria os assignments por skill (LABOR) e atualiza para RELEASED.

**Fluxo resultante:**
```
PENDING_OA -- btn_aprovar_cliente --> APPROVED (Aprovado p/ Cliente)
                                       |
                         btn_liberar_para_execucao (grid)
                                       v
                        RELEASED + assignments por skill criados
```

**Status afetados:** `APPROVED` ja existia e continua compativel com o `mro_engine` (lista `RELEASED, PENDING_OA, APPROVED, COMPLETED, CLOSED`).

### Gap ① — mesmo problema no `mro_engine.php` (Bug 1 — EXTENSÃO, AGUARDANDO DECISAO DO SUPERIOR)

**ANOTACAO PARA AVALIACAO** — o mesmo problema do Bug 1 (pular direto para `RELEASED` sem criar assignments) tambem ocorre no **motor O&A** (`_Bibliotecas_Internas/mro_engine.php`), no cenario de **auto-approve**:

```php
// Se a tarefa estava bloqueada aguardando o cliente (PENDING_OA), e o custo baixou, aprova automatico!
if ($status_atual == 'PENDING_OA') {
    $novo_status = 'RELEASED';   // <-- MESMO BUG: pula para RELEASED
    // log 'AUTO_APPROVE' registrado
}
```

**Impacto:** quando a NRC esta em `PENDING_OA` e o motor detecta que o custo **baixou** (revisao automatica do CAP), ele aprova sozinho e manda direto para `RELEASED` — **sem passar por `APPROVED`** e **sem criar assignments** (quem cria assignments e o `btn_liberar_para_execucao`, que so processa `PLANNING/NOT_STARTED/PLANNED/APPROVED`, **nao RELEASED**). Resultado: NRC liberada orfa de mao de obra (mesmo sintoma do Bug 1).

**Opcao de correcao (se aprovada pelo superior):** trocar `$novo_status = 'RELEASED'` por `$novo_status = 'APPROVED'` no trecho acima, mantendo consistencia com o novo fluxo do MRO-122:

```
PENDING_OA -- auto-approve motor O&A --> APPROVED -- btn_liberar_para_execucao --> RELEASED + assignments
```

**Status: RESOLVIDO (decisao do superior: motor O&A deve criar os assignments antes de RELEASED)** — implementado em `_Bibliotecas_Internas/mro_engine.php`:

> 📄 Detalhamento completo (bug, solução, teste e correção fina): [ajuste-motor-oa-assignments.md](ajuste-motor-oa-assignments.md)

1. **Nova funcao `fn_criar_assignments_por_skill($v_task_id, $v_projeto_atual)`** — busca recursos LABOR de `mro_task_resources`, cria os slots em `mro_task_assignments` (NOT_STARTED) com protecao contra duplicidade (verifica se a skill ja possui assignment). Fallback: cria alocacao generica com o skill_code da task.
2. **Chamada no auto-approve** — antes do UPDATE para RELEASED (ambos os pontos: `PENDING_PROG` e `PENDING_OA`):

```php
// MRO-122: Ao liberar automaticamente (dentro do CAP), cria os assignments
if ($novo_status == 'RELEASED') {
    fn_criar_assignments_por_skill($v_task_id, $v_projeto_atual);
}
```

**Fluxo resultante (auto-approve):**
```
PENDING_PROG / PENDING_OA -- motor O&A (dentro do CAP) --> RELEASED + assignments por skill
```

### Gap ② — Auto-approve "Dentro do CAP" tambem nao cria assignments

**ANOTACAO PARA AVALIACAO** — alem do Bug 1 — EXTENSÃO (①), ha outro ponto no fluxo de NRC com o **mesmo sintoma**: quando a NRC esta **dentro do CAP** do contrato, o `btn_validar_prog` → `fn_calcular_oa_nrc()` faz auto-approve e manda direto para `RELEASED`:

```php
// NÃO ESTOUROU O CAP (Dentro do orcamento)
// MRO-117: Se veio da Programacao (PENDING_PROG), libera direto.
if ($status_atual == 'PENDING_PROG') {
    $novo_status = 'RELEASED';   // <-- MESMO GAP: pula para RELEASED sem assignments
    // log 'AUTO_APPROVE' registrado
}
```

**Impacto:** a NRC fica em `RELEASED` **sem assignments**. Como o `btn_liberar_para_execucao` do grid so processa `PLANNING/NOT_STARTED/PLANNED/APPROVED` (e **nao** `RELEASED`), ninguem consegue criar assignments depois. A NRC fica orfa de mao de obra permanentemente.

**Diferenca do Gap ①:** o Gap ① ocorre quando a NRC ja estava em `PENDING_OA` e o custo baixou. O Gap ② ocorre na **primeira validacao** da Programacao (`PENDING_PROG`), quando o custo ja esta dentro do CAP desde o inicio — cenario ainda mais comum.

**Caminho afetado no diagrama:**
```
PENDING_PROG -- btn_validar_prog --> Dentro do CAP? -- Sim ① --> RELEASED (sem assignments!)
```

**Opcao de correcao (se aprovada pelo superior):** em vez de `$novo_status = 'RELEASED'`, ir para `APPROVED` (ou adicionar logica para criar assignments diretamente no `fn_calcular_oa_nrc`), garantindo que o fluxo sempre passe por um ponto que crie assignments.

**Status: RESOLVIDO** — mesma implementacao do Gap ① (decisao do superior): o `mro_engine.php` agora chama `fn_criar_assignments_por_skill()` antes de mudar para `RELEASED` no auto-approve. Cobre tanto `PENDING_PROG` quanto `PENDING_OA`. Teste: NRC dentro do CAP validada pelo `btn_validar_prog` cria os slots por skill ao liberar automaticamente. (Detalhes: [ajuste-motor-oa-assignments.md](ajuste-motor-oa-assignments.md))

### Gap ③ — Rotina: SUPSIG → CLOSED nao implementado

**ANOTACAO PARA AVALIACAO** — o status `CLOSED` **nao existe** na tabela `mro_sys_status`. Confirmado via query: `SELECT status_code FROM mro_sys_status WHERE status_code = 'CLOSED'` retornou 0 linhas.

O `control_pause_task` (motivo 6, conclusao) manda o **assignment** para `SUPSIG`. Porem:
- Nao ha codigo que faca `SUPSIG → CLOSED` para assignment ou task
- A grid `grid_public_mro_task_assignments_completed` lista assignments em `SUPSIG`/`PENDING_HANDOVER` mas esta com **eventos vazios** (nenhuma implementacao)
- Assignments concluidos pelo mecanico ficam em `SUPSIG` **indefinidamente**, sem transicao para um status terminal

**Impacto:** o ciclo de vida do assignment nunca fecha formalmente. Nao ha "assinatura digital" do supervisor/qualidade implementada.

**Sugestao:** implementar botao/evento na `grid_public_mro_task_assignments_completed` que muda assignment de `SUPSIG` para um status terminal. Se necessario, criar `CLOSED` no `mro_sys_status`.

**Status:** PENDENTE — aguardando implementacao.
